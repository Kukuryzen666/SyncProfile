## 1. Архитектура и ключевые компоненты

SyncProfile построен на стыке **Python (Chaquopy)** и **Java (Android Telegram Client)**:
- **`TLRPC` объекты**: Базовые структуры данных Telegram (`TLRPC.User`, `TLRPC.Chat`, `TLRPC.UserFull`, `TLRPC.TL_peerColor`, `TLRPC.TL_emojiStatus`).
- **`MessagesController`**: Центральный синглтон управления сообщениями, пользователями и чатами. Модификация TL-объектов происходит через хуки методов `getUser`, `getChat`, `putUser`, `putChat`, `putUsers`, `putChats`.
- **Синхронизация с сервером**:
  - `_api_request`: Единый HTTP-клиент с retry и exponential backoff.
  - `_sync_database` (`GET /api/profiles/all`): Полная загрузка базы.
  - `_sync_delta_worker` (`GET /api/profiles/updates?since=TS`): Дельта-синхронизация каждые 30 секунд.
- **Двухуровневый кэш**:
  - `_profiles_snapshot` / `_chats_snapshot`: Неизменяемые словари (dict snapshots) для O(1) потокобезопасного чтения из UI-потока без блокировок.
  - `_profiles_cache` / `_chats_cache`: Рабочие словари, защищенные `_sync_lock`.
  - Дисковый JSON-кэш (`sync_profiles_cache.json`) с debounce записью.

## 2. Различия между AyuGram и exteraGram

| Аспект | AyuGram (`sync_ayugram.plugin`) | exteraGram (`sync_exteragram.plugin`) |
| :--- | :--- | :--- |
| **Local Premium пользователя** | Управляется **исключительно AyuConfig** (нативная система клиента). Плагин **не имеет права** перезаписывать `AyuConfig.nameColor`, `statusEmojiId`, `profileColor`. | Управляется плагином через `ExteraConfig.localPremium`, но **строго ограничено правами профиля на сервере SyncProfile**. |
| **Собственный аккаунт** | Плагин считывает настройки из `AyuConfig` и отправляет их на сервер SyncProfile. | Плагин отправляет слот-настройки `slot_N` на сервер. |
| **Обработка чужих пользователей** | Патчит TL-объекты пользователей и каналов из базы SyncProfile. | Патчит TL-объекты пользователей и каналов из базы SyncProfile. |
| **Всплывающее меню в профиле** | Telegram Bulletin внизу экрана (`bulletins.show_info`). | Telegram Bulletin внизу экрана (`bulletins.show_info`). |

## 3. Реестр багов, первопричины и решения

### Баг 1: Вылет в «Все чаты» и сброс навигации
- **Симптом**: При пролистывании сообщений, наборе текста или смене папок текущий чат закрывался, а приложение выбрасывало в корень списка диалогов («Все чаты»).
- **Первопричина**: Вызов `MessagesController.getInstance(account).getUser(Long)` или отправка событий в `NotificationCenter.updateInterfaces` из Python триггерила глобальную перерисовку `DialogsActivity`. Telegram считал, что список диалогов полностью обновился, и сворачивал текущий `ChatActivity` фрагмент.
- **Правило**:
  - ❌ **Никогда** не вызывать `mc.getUser()` и не отправлять уведомления в `NotificationCenter` из фоновых или UI-методов плагина для обновления интерфейса.
  - ✅ TL-объекты модифицируются **только** на лету в хуках `getUser`, `getChat`, `putUser`, `putChat`, `putUsers`, `putChats`.

---

### Баг 2: Конфликт хуков AlertsCreator и падение при вводе эмодзи
- **Симптом**: При попытке вставить премиум эмодзи или нажать на статус приложение падало (NPE) или выбрасывало в список чатов.
- **Первопричина**: Хук на `AlertsCreator.showCustomEmojiPremiumAlert` возвращал `param.setResult(None)`. Клиент ожидал объект `Dialog`/`BottomSheet`, и вызов `.show()` или проверка на null в коде Telegram приводила к `NullPointerException`.
- **Правило**:
  - ❌ **Не вешать хуки на методы создания диалогов/алертов**, если метод должен вернуть объект UI.
  - ✅ Подавление диалогов допустимо только если метод возвращает `void` или `boolean`.

---

### Баг 3: Перезапись нативного Local Premium в AyuGram
- **Симптом**: При включённом плагине в AyuGram сбрасывались или блокировались локальные цвета, эмодзи-статусы и нативные премиум-функции собственного аккаунта.
- **Первопричина**:
  1. Плагин помещал собственные UID в `_profiles_cache` со значениями слота по умолчанию (`name_color=0` / Красный, `emoji_status=None`).
  2. `_patch_user_tl_object` и `_patch_full_user_tl_object` перехватывали `currentUser` и принудительно перезаписывали его поля `color`, `profile_color`, `emoji_status`, а также выставляли невалидный флаг `flags2 |= 0x8`.
- **Правило**:
  - ❌ В AyuGram плагин **никогда не модифицирует `AyuConfig` и никогда не патчит TL-объекты собственного аккаунта** (`_patch_user_tl_object` и `_patch_full_user_tl_object` немедленно завершаются с `False` для `uid in self._own_uids_cache`).
  - ❌ Собственные аккаунты **никогда не помещаются в `_profiles_cache`**.
  - ✅ В AyuGram собственный профиль на 100% управляется клиентом, плагин лишь транслирует чужие профили из базы SyncProfile.

---

### Баг 4: Исчезновение значков/флагов без кастомного цвета
- **Симптом**: Пользователь установил эмодзи-значок (флаг страны, значок клана и т.д.), но оставил цвет по умолчанию. Значок не отображался на AyuGram.
- **Первопричина**: В `_build_peer_color` стояло условие `if c < 0: return None`. Если `color_id` был равен `-1` (цвет по умолчанию), функция возвращала `None`, и `TL_peerColor` с фоновым эмодзи (`background_emoji_id`) отбрасывался.
- **Правило**:
  - ✅ В `_build_peer_color`:
    ```python
    bg = _safe_int(bg_emoji_id, 0)
    c = _safe_int(color_id, -1) if color_id is not None else -1
    if c < 0 and bg == 0:
        return None
    if c < 0:
        c = 0  # базовый индекс при наличии значка
    ```

### Баг 5: Пропуск перегрузок MessagesController из-за раннего выхода
- **Симптом**: Значки и эмодзи-статусы отображались в exteraGram, но не отображались в AyuGram в сообщениях и списке чатов.
- **Первопричина**: В `MessagesController` есть перегрузки `getUser(long)` (примитив) и `getUser(Long)` (объект). В коде стоял флаг `user_hooked = True`. После перехвата `getUser(Long)` цикл прекращал поиск, и вызовы UI AyuGram через `getUser(long)` шли без патчинга.
- **Правило**:
  - ❌ Не использовать boolean-флаги для ограничения хуков одиночными методами.
  - ✅ Хукать **все перегрузки** с регистрацией по сигнатуре `(m_name, tuple(param_types))`.

---

### Баг 6: Пропуск участников групп из-за отсутствия хука на putUsers
- **Симптом**: В больших чатах и каналах пользователи из базы SyncProfile отображались как обычные пользователи без цвета и статусов.
- **Первопричина**: Telegram при загрузке участников чата вызывает пакетный метод `putUsers(ArrayList<TLRPC.User> users, boolean fromCache)`. Без хука на этот метод пользователи попадали в кэш без профиля SyncProfile.
- **Правило**:
  - ✅ Обязательно перехватывать `putUsers` и `putChats` и патчить все элементы переданных коллекций.

---

### Баг 7: Повреждение структуры User из-за флага flags2 |= 1
- **Симптом**: Пропадали или ломались юзернеймы пользователя в карточке профиля.
- **Первопричина**: В `TLRPC.User` бит 0 поля `flags2` (`flags2 & 1`) отвечает за `usernames:Vector<Username>`. Выставление `new_flags2 |= 1` повреждало маску структуры.
- **Правило**:
  - ✅ Для `TLRPC.User`: эмодзи-статус выставляется **только** в `flags.30` (`new_flags |= 0x40000000`). Поле `flags2` для статуса пользователя не используется!
  - ✅ Для `TLRPC.Chat`: эмодзи-статус выставляется в `flags.9` (`512`), `flags2.0` (`1`), `flags2.10` (`1024`).

### Баг 8: Зависание/лаг при открытии ProfileActivity и загрязнение описания («О себе»)
- **Симптом**: При тапе на профиль интерфейс зависал на 200–500 мс перед открытием, а в описании («О себе») появлялся текст `⚡ Этот пользователь использует SyncProfile`.
- **Первопричина**:
  1. `_patch_full_user_tl_object` перезаписывал поле `fu.about`, загрязняя биографию пользователя.
  2. Рекурсивный поиск `_find_profile_info_layout` проходил по дереву Android ViewGroup (до 6 уровней вглубь) с JNI-вызовами `getClass().getSimpleName()` на каждом элементе при каждом открытии профиля.
- **Правило**:
  - ❌ **Никогда** не модифицировать поле `fu.about` / `fc.about`.
  - ❌ **Никогда** не делать рекурсивных обходов View-дерева в рантайме.
  - ✅ Показывать нативное всплывающее меню Telegram Bulletin снизу экрана (`bulletins.show_info`) в хуке `ProfileActivity.onResume` с 10-секундным кулдауном.

### Баг 9: Блокировка кнопки «Сбросить кэш и перекачать базу»
- **Симптом**: При нажатии «Сбросить кэш и перекачать базу» выводилось сообщение «Синхронизация уже выполняется...», база не скачивалась, а профили не обновлялись.
- **Первопричина**:
  1. Фоновый цикл держал лок `_sync_in_progress = True`.
  2. В памяти оставались заполненными множества `_untracked_uids` и `_untracked_cids`, из-за чего пользователи продолжали считаться отсутствующими в базе.
  3. Несоответствие формата ответа сервера (список vs словарь).
- **Правило**:
  - ✅ В `_clear_cache_action` принудительно сбрасывать `_sync_in_progress = False`.
  - ✅ Очищать `_untracked_uids`, `_untracked_cids`, `_video_checked_uids`, `_video_checked_chat_ids`.
  - ✅ Использовать `_parse_items_map` для поддержки любых форматов ответов сервера.

### Баг 10: Просадки FPS при скролле списка чатов (Chaquopy JNI Overhead)
- **Симптом**: Микрофризы и просадки частоты кадров при быстром скролле списка чатов.
- **Первопричина**: Проверки `_is_user(obj)` и `_is_chat(obj)` использовали `hasattr(obj, "first_name")` и `hasattr(obj, "title")`. Каждый `hasattr` на Java-объекте через Chaquopy делает JNI-запрос reflection. При 100 сообщениях на экране это вызывало тысячи JNI-вызовов в секунду.
- **Правило**:
  - ✅ Использовать O(1) проверку имени класса (`cls_name in ("TL_user", "TL_user_layer", ...)`).
  - ✅ Кэшировать результат патчинга в поле `_sp_v = (cache_version, uid)`: повторный вызов функции патчинга завершается за 1 проверку без JNI.

### Баг 11: Утечки памяти и бесконечный рост множеств кэша
- **Симптом**: Постепенное увеличение потребления RAM клиентом при долгой работе.
- **Первопричина**: Множества `_untracked_uids`, `_untracked_cids`, `_video_checked_uids`, `_video_checked_chat_ids`, `_PATCHED_MSGS`, `_FIND_CLASS_CACHE` росли без ограничений.
- **Правило**:
  - ✅ В методе `_trim_memory_caches()` установлены строгие лимиты (5000 UID, 2000 CID, 2000 сообщений, 200 классов, 500 цветов), вызываемые в конце каждого цикла синхронизации.

---

### Баг 12: Лаги и исключения в UI-потоке exteraGram
- **Симптом**: Пролагивания интерфейса exteraGram при возврате в приложение (resume) и открытии профилей.
- **Первопричина**:
  1. В `on_app_event` и `_apply_all_to_all_accounts` вызывался метод `_sync_local_ayuconfig()`, отсутствующий в exteraGram, вызывая `AttributeError` на главном UI-потоке.
  2. В `_patch_user_tl_object` при проверке неотслеживаемых пользователей происходил синхронный JNI-вызов `_get_my_active_uids()` (перебор всех аккаунтов через reflection).
  3. `_ensure_local_premium()` при каждом возобновлении приложения повторно сканировал классы JVM вместо использования глобального кэша `_EXTERA_CONFIG_CLASS`.
- **Правило**:
  - ✅ В exteraGram исключены любые обращения к AyuGram-специфичным функциям.
  - ✅ Проверка собственных аккаунтов в hot-path `_patch_user_tl_object` выполняется строго по in-memory множеству `_own_uids_cache` без JNI-fallback.

### Баг 13: Повреждение кастомных эмодзи в каналах и конфликт с Local Premium в AyuGram
- **Симптом**: При отправке постов с премиум-эмодзи в каналы из AyuGram эмодзи мгновенно превращались в дефолтные Unicode-эмодзи, тогда как без плагина всё отправлялось корректно.
- **Первопричина**: В `sync_ayugram.plugin` был зарегистрирован `on_send_message_hook` и перехватчик `pre_request_hook` на `messages.sendMessage` / `messages.sendMedia`, который принудительно переписывал `TL_messageEntityCustomEmoji` в `TL_messageEntityTextUrl` (`tg://emoji?id=...`). В AyuGram отправка кастомных эмодзи поддерживается нативно на уровне клиента (`AyuConfig` / Local Premium). В каналах ссылки `tg://emoji` ломали пост, превращаясь в дефолтный эмодзи.
- **Правило**:
  - ❌ В AyuGram (`sync_ayugram.plugin`) плагин **никогда не перехватывает и не модифицирует исходящие сообщения** (`on_send_message_hook` и `pre_request_hook` возвращают `DEFAULT`).
  - ✅ Перехват исходящих сообщений с конвертацией в `tg://emoji` разрешён **только** в `sync_exteragram.plugin`, где нативная отправка кастомных эмодзи отсутствует.
  - ✅ Входящий парсинг (`post_request_hook` / `on_updates_hook`) остаётся активным в обоих плагинах для совместимости между клиентами.

### Баг 14: Пропуск основного аккаунта при входе с твинка в AyuGram (Multi-account collision)
- **Симптом**: Если на одном клиенте AyuGram авторизовано несколько аккаунтов (например, Слот 0 — Основа и Слот 1 — Твинк), то при входе с Твинка в чатах и диалогах Основной аккаунт отображался полностью дефолтным (без цветов, фонов и статусов).
- **Первопричина**:
  - `_own_uids_cache` собирал ID всех активных аккаунтов устройства (`{UID_main, UID_twink}`).
  - В `_patch_user_tl_object`, `_patch_full_user_tl_object`, `post_request_hook`, `on_updates_hook` стояла жесткая проверка `if uid in self._own_uids_cache: return False`.
  - При просмотре с Твинка нативный `AyuConfig` клиента управляет **только активным аккаунтом** (Твинком), а для Основы плагин блокировал применение настроек из базы.
- **Решение**:
  - Убрана блокировка `if uid in self._own_uids_cache: return False`.
  - Профиль любого пользователя (включая основу), присутствующего в снимке базы `_profiles_snapshot`, гарантированно применяется.

## 4. Инварианты и правила для разработчиков

1. **Никаких блокирующих операций в UI-потоке**:
   - Все сетевые запросы (`_api_request`) и работа с диском — строго в background-потоках (`threading.Thread` или `async_manager.run_task`).
2. **Изоляция снимков состояния (Snapshots)**:
   - UI-поток читает **только** из `_profiles_snapshot` и `_chats_snapshot`. Эти словари атомарно подменяются при обновлениях базы и не требуют захвата блокировок.
3. **Безопасность хуков (MethodHook)**:
   - Внутри хуков весь код должен быть обёрнут в `try...except Exception: pass`. Ошибка в плагине ни при каких обстоятельствах не должна приводить к крэшу хост-приложения Telegram.
4. **Сохранение целостности пользовательских данных**:
   - Запрещено менять `about`, `phone`, `username`, `first_name`, `last_name` реальных пользователей.
5. **Соблюдение битовых масок TLRPC**:
   - Любое изменение флагов `flags` и `flags2` должно строго сверяться со схемой Telegram MTProto (`schema.tl`).
